# CC Switch 无内置供应商自动构建

本目录维护对上游的有限清理补丁及自动发布流程。应用代码来自 `farion1231/cc-switch` 的最新正式 Release；每次运行先锁定该版本的完整提交 SHA，再应用补丁、验证并构建。

## 清理范围

- 移除应用中的内置供应商推荐、预设入口和供应商推广展示。
- 阻止首次启动自动生成默认供应商卡片。
- 保留用户自行添加或导入的供应商、已有本地配置、网站协议导入、账户认证与其余上游功能。
- 应用升级与下载入口指向本仓库，避免更新后回到官方内置供应商版本。

补丁修改范围由 `scripts/verify-clean.py` 和审计清单限制。上游结构不再符合已审计条件、补丁无法应用、回归测试失败或任一平台构建失败时，本次发布停止，已发布版本保持不变。未来上游新增供应商入口或重构相关模块时，可能需要维护补丁。

## 自动流程

工作流：`.github/workflows/clean-release.yml`。

1. 每隔 6 小时读取上游最新正式 Release，排除草稿和预发布版本。
2. 解析 Release 对应的 Git 提交，不直接从不断变化的 `main` 构建。
3. 检查本仓库是否已发布对应清理版本；已发布则结束，不重复构建。
4. 应用清理补丁和独立更新配置，运行源码检查、TypeScript 检查、相关前端回归测试和前端生产构建。
5. 将经过验证的应用源码打成带 SHA-256 校验的统一快照。所有原生平台从同一快照构建；Linux x64 还运行启动、官方账户按需恢复及本地配置导入回归测试。
6. 构建 Windows x64 / ARM64、Linux x64 / ARM64、macOS Universal 安装包。
7. 校验各平台产物齐全，上传到草稿 Release；所有附件上传完成后，发布为最新正式版。

北京时间计划检查时间为 **02:17、08:17、14:17、20:17**。GitHub 定时任务可能延迟；这不是实时上游推送。也可以在 Actions 的 **Clean upstream release → Run workflow** 手动运行。修改 `.clean/` 或本工作流并推送至 `main` 时也会检查一次。

发布标签类似 `clean-v4.0.35-r1`，避免与仓库原有的 `v*` 发布流程冲突。内部应用版本及安装包基础名称仍使用官方 `4.0.35` / `v4.0.35`。

## 当前默认：私有仓库，自动发布，手动安装

此仓库目前为私有仓库。默认配置可以自动生成并发布安装包，用户登录 GitHub 后下载。

以下两项与官方发行包存在明确区别：

1. **应用内更新尚未配置。** GitHub 私有 Release 不能被应用匿名下载，而独立更新签名需要自己的密钥。默认构建保留上游更新代码，但将更新端点设为空，并关闭更新包签名产物生成；不会使用任何官方更新源。此时在客户端中检查/安装自动更新不会工作，应从本仓库 Releases 手动覆盖安装。
2. **macOS 默认使用 ad-hoc 签名，不含 Apple 公证。** Universal DMG / ZIP 可以构建，但首次启动可能需要在 macOS 隐私与安全设置中允许。只有配置自己的 Apple 凭据后，才构建并验证 Developer ID 签名、公证版本。

因此，“GitHub 自动跟随并发布”与“已安装客户端自动更新”是两个独立阶段。不能将默认私有仓库配置描述为已经实现官方发行包的完整更新体验。

## 配置独立的应用内更新

当前工作流支持**本仓库公开可读的 GitHub Release**作为更新源。配置签名前，必须先由仓库所有者决定公开发行方式；工作流不会自行修改仓库可见性。

如果继续保持源码仓库私有而希望公开安装包，需要另行配置公开发布仓库或资源存储，以及对应上传流程。仅填写外部 URL 而不发布可公开访问的安装包不够；当前流程会拒绝这种不完整配置。

在仓库 Settings → Secrets and variables → Actions 设置：

| 类型 | 名称 | 内容 |
| --- | --- | --- |
| Variable | `TAURI_PUBLIC_KEY` | 自己生成的 Tauri/minisign 公钥，可填写 `.pub` 文件内容 |
| Secret | `TAURI_SIGNING_PRIVATE_KEY` | 对应的私钥文件内容 |
| Secret，可选 | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥密码；未加密时留空 |
| Variable，可选 | `CLEAN_UPDATE_ENDPOINT` | 只能是 `https://github.com/<owner>/<repo>/releases/latest/download/latest.json`；默认按当前仓库生成 |

公钥与私钥必须属于同一对。可在安装了项目依赖的可信本地环境使用 `pnpm tauri signer generate -w <私钥保存路径>` 生成，然后分别保存公钥和私钥。私钥仅放入 GitHub Secrets，并在自己的安全位置保留备份；不要提交到 Git，也不要发送到聊天或日志。

工作流会匿名验证仓库是否公开可读；私有仓库会在原生构建之前停止签名更新模式。发布时还会用公钥验证每份更新产物的真实 minisign 签名，再生成 `latest.json`，避免错误密钥对导致客户端无法升级。

首次从官方版或未配置更新的旧版切换到本构建，需要手动安装一次。后续新的官方版本，在独立签名与公开更新源配置正确时，沿用上游客户端的更新行为；不会绕过用户对安装的确认。

## 可选：macOS Developer ID 与公证

以下五个 Secrets 必须一起提供；都不提供则使用 ad-hoc 签名。部分配置会直接失败，避免误称为已公证。

| Secret | 内容 |
| --- | --- |
| `APPLE_CERTIFICATE` | 导出的 Developer ID Application `.p12` 文件的 Base64 内容 |
| `APPLE_CERTIFICATE_PASSWORD` | `.p12` 文件密码 |
| `APPLE_ID` | Apple 账号 |
| `APPLE_PASSWORD` | Apple 应用专用密码 |
| `APPLE_TEAM_ID` | Apple Team ID |

工作流使用临时钥匙串，构建后删除；不会使用或复制上游作者的签名凭据。Apple 拒绝凭据、证书或开发者协议时，工作流失败，需由账号所有者处理后重新运行。

## 版本、源码与可追溯性

`config.json` 中的 `release_revision` 默认为 `1`。只有修改清理补丁、发布方式或构建配置并希望为同一个官方版本重新发布时，才递增为 `2`、`3`。后续官方版本会自动使用当前清理修订号，无需每次修改配置。

应用内部版本不额外改写，因此 `clean-v4.0.35-r1` 与 `clean-v4.0.35-r2` 的应用内部版本都是 `4.0.35`；这种清理修订不会触发 SemVer 自动升级，必须手动覆盖安装。官方从 `4.0.35` 升到 `4.0.36` 时，签名更新模式可以正常识别新版本。

本仓库现有 `main` 代码和历史不被自动覆盖。发布标签标记自动化配置提交，所以 GitHub 自动提供的 **Source code (zip/tar.gz)** 是自动化仓库状态，不能当成本次应用构建源码。

每个 Release 单独附带：

- `CC-Switch-v<版本>-Clean-Source.tar.gz`：与所有平台安装包对应的完整、已应用补丁的应用源码。
- `clean-build-provenance.json`：上游版本与 SHA、自动化提交、清理修订、更新配置、构建源码校验及产物校验。
- `SHA256SUMS.txt`：附件的 SHA-256 校验值。

所有平台的产物清单必须引用同一个源码快照 SHA。已发布的 Release 不被覆盖；同一标签的草稿只在来源提交一致时续传。

## 维护与故障处理

- Actions 没有开始：检查工作流是否启用、账户 Actions 额度和仓库策略；定时工作流只从默认分支运行。
- 补丁或审计失败：先检查上游相关变更，更新有限补丁及审计规则，保留回归测试，再递增清理修订号。不要为了继续发布而删除审计检查。
- 测试或构建失败：查看失败平台日志，修复后重新运行；未完成的版本不会成为最新 Release。
- 私钥、公钥、公开更新源部分配置：补全全部必要条件，或回到明确的手动安装模式。不会静默降级签名模式。
- 已发布同名清理版本：例行检查直接结束。需要修改产物时递增 `release_revision`，避免覆盖已发安装包。

GitHub 工作流本身使用仓库的 `GITHUB_TOKEN`，不需要为本仓库自动构建和发布额外提供个人访问令牌。流程在同一次工作流中完成，不依赖机器人推送标签触发另一个工作流。
